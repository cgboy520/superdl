# One-shot node join

The script itself lives at **`apps/api/app/modules/nodes/assets/node-join.sh`** (packaged with the API image and served by `GET /api/v1/node-enroll/script`; the server only replaces the `__API_BASE__` placeholder). This directory holds only tests and documentation, never a second copy of the script.

## Usage (operator view)

1. A super admin enters once under admin "Platform configuration · Cluster access": the server address (HA clusters use the control-plane VIP: RKE2 `https://<vip>:9345`; a single k3s server `https://<server-ip>:6443`), the join token (the dedicated **agent token**: the `agent-token` value of the server config; **never** `/var/lib/rancher/<rke2|k3s>/server/node-token`, see deploy/cluster/README.md "Server token and agent token"), the agent version and the driver version; registries.yaml is generated by the platform from "Platform configuration · Image registry" (Spegel + Harbor proxy cache + self-signed CA, no credentials; an advanced override can be typed by hand).
2. Ops picks a pool under admin "Nodes and GPUs · Add node" and generates a one-time command (valid 24 h by default, shown once):
   ```bash
   echo 'sdln_xxx' | sudo sh -c 'umask 077; cat > /run/superdl-join.token; curl -fsSL https://<api>/api/v1/node-enroll/script | bash -s -- --token-file /run/superdl-join.token; s=$?; rm -f /run/superdl-join.token; exit $s'
   ```
   The token reaches a 0600 file under `/run` (tmpfs) through stdin; the script reads the token only from that file, it never enters any process argv, and the file is deleted when the run ends.
3. Paste and run on the new server; the admin "Pending nodes" view shows the stage progress live (script output and progress reports are always English). The server host of a light single-machine setup uses the same command: when the script detects the running server service it installs no agent and changes no server configuration, only applies the node baseline and the pool label (see `docs/reference/nodes.md`). The kata pool includes one automatic reboot (a systemd oneshot resumes from the checkpoint). On failure fix the environment and re-run the same command (resume from checkpoint); re-running after the node has joined exits at once, a full reinstall needs `--force` + a fresh token issued by the admin console.

Security model: the script itself contains no secrets; the server address and join token are exchanged for the enrollment token via `POST /bootstrap` (Bearer; the token is 256-bit, only its hash is stored, absolute expiry, any invalid token answers 404). The enrollment token is **single-use**: the first bootstrap consumes it and issues a narrow progress token (may only report progress), stored at `/var/lib/superdl-node-join/token` (0600) for resuming; it is deleted together with bootstrap.json when the install completes. The k3s/rke2 installers are downloaded from fixed URLs and verified against the script's built-in sha256 pins before running; when executed through a pipe, the script re-fetches itself from the API before the reboot and verifies the script_sha256 delivered by bootstrap (missing or mismatched aborts). Rotation of the join token (= agent token) is in deploy/cluster/README.md "Server token and agent token" (`token rotate` rotates only the server token).

File permissions: `umask 077` up front, the log explicitly 0644.
Uninstall: `sudo bash node-join.sh --uninstall` reverses the install (agent, the sysctl / GRUB / blacklist / cluster configuration written by this script, the state directory) without touching the superdl-nvme VG or the driver; retiring the node still needs `kubectl delete node` on the platform side.

## Tests

The bats cases under `deploy/node-join/tests` fake system commands with PATH shims and never touch the real system; the command is in CLAUDE.md "Common commands".

Every system path the script reads is overridable through `SUPERDL_JOIN_*` environment variables (state directory / `/etc` / loop image directory / IOMMU group directory / `SUPERDL_JOIN_OS_RELEASE` / `SUPERDL_JOIN_CPUINFO`); bats points them at temporary directories in setup; `SUPERDL_JOIN_IOMMU_ARGS` overrides the IOMMU kernel arguments derived from the CPU vendor. The distribution baseline is the Debian family (`ID` ubuntu / debian or `ID_LIKE` containing debian); other distributions are refused at precheck. **New code that reads host paths must add an override point the same way.**
Numeric defaults follow the same rule: `SUPERDL_JOIN_NVCTK_MIN_VERSION` (nvidia-container-toolkit minimum version, default 1.17.8) and `SUPERDL_JOIN_POD_PIDS_LIMIT` (kubelet per-Pod PID cap, default 4096, the same value as the rke2/k3s server configuration).

Installer source: `node_install_mirror` defaults to `official`, `cn` is the explicit option for the mainland-China mirror; an unknown value is refused at agent_install.

Coverage: argument errors / installer source (official rke2 + k3s by default, explicit cn, unknown value refused, pin mismatch prints the digests, cn pins match ansible) / distribution gate (non-Debian refused, ID_LIKE derivatives accepted) / IOMMU arguments per CPU vendor (Intel / AMD / unknown vendor fail-closed + explicit override) / full flow without reboot / token never in argv and cleaned up on completion / agent config refused when the join token contains a newline or is the server node-token / re-run after completion exits at once / --force reinstall / resume from checkpoint (token switch) / reboot checkpoint (oneshot + token 0600) / piped execution re-fetches the script and verifies its fingerprint / installer pin mismatch refused / reboot loop protection / kata GRUB IOMMU / k3s mode placement (podPidsLimit included) / installer source cn and official / unregistered NVMe gets no fallback / explicit loop registration / toolkit minimum version (skip when met, install when missing, fail when still too low after install, env override effective).
Real-hardware validation is in `deploy/cluster/runbooks/cluster-validation.md`; the node domain is described in `docs/reference/nodes.md`.
