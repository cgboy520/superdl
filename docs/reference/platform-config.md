# Platform configuration centre

Channel credentials, security switches, site compliance information, cluster access and operations policy parameters are entered online in the admin console and take effect immediately. The mechanism is in `app/core/platform_config.py`: one `SETTING_SPECS` allow-list, one `platform_settings` table, one strongly typed read surface `RuntimeConfig`.

## Data model

- `platform_settings`: `key` (PK), `value` (Text, secrets as `enc:v2:` ciphertext), `updated_by`, `updated_at`

## Deployment identity

Three values are deployment identity, not online settings: they live only in env (`Settings`, not `SETTING_SPECS`), are published read-only on `GET /platform-config` (`deployment`) and `/site-config`, and in prod must be set explicitly.

- `SUPERDL_COMPLIANCE_PROFILE` (`none` | `cn`; `app/core/compliance.py`): which regional rules apply. `none` = international default (phone optional, no identity-verification form, no invoice tax-ID rule, default locale en-US). `cn` = mainland China (phone required with dial code +86, `cn_id_card` KYC form, `cn_uscc` tax-ID rule, default locale zh-CN). Unset resolves to `none` outside prod; prod refuses to boot without it.
- `SUPERDL_WEB_BASE_URL` (user console origin, default `http://localhost:5173`; prod requires https when the API mounts payment secrets): payment return URLs `{web_base_url}/billing?recharge=<order_no>` are built from it.
- `SUPERDL_PLATFORM_CURRENCY` (ISO 4217, default `USD`; table `app/core/currencies.py`, 0- and 2-decimal currencies only) and `SUPERDL_BILLING_TIMEZONE` (IANA zone, default `UTC`) are validated at startup in every environment and locked in the single-row table `billing_identity` on first boot (`billing.identity.assert_billing_identity`, called by the API lifespan and the worker). A later env change is accepted only while no `balance_ledger` / `orders` / `bills_hourly` / `bills_daily_disk` row exists, or with `SUPERDL_BILLING_IDENTITY_REKEY=true`; otherwise the process refuses to start. New `orders` rows record `currency` = platform currency.

## Rules and invariants

- `SETTING_SPECS` is an allow-list: unknown keys are always rejected; the write entry points are isolated by group (`/policies` accepts only the policy group, `/platform-config` never accepts it). Values are env default + DB override; non-empty env-layer values pass the same format validation at startup (`env_layer_problems`, prod refuses to boot on failure). Every write counts `superdl_platform_config_write_total{domain}` per group, and every write to the payment / crypto groups alerts `PaymentConfigWritten`.
- The effective configuration is not cached in-process (`get_runtime_config` → `RuntimeConfig`; the admin display uses the string map `effective_strings`): every read is a full SELECT + decrypt, a write takes effect immediately; a row whose ciphertext fails to decrypt fails closed with an error, never silently falls back to env. Business code reads only the typed `RuntimeConfig` fields and never compares the string `"true"`.
- Prod-forbidden values (`SettingSpec.prod_forbidden`) are the single source of truth: online writes and override clears are refused, the configuration page shows a red badge (`compute_config_warnings`, `prod_gate=True` keys are error, the rest warning), and the boot compliance gate (`assert_prod_compliance_gates`, looking only at `prod_gate=True` keys) all derive from it. `prod_forbidden_profiles` narrows a rule to the listed compliance profiles: `captcha_enabled` / `real_name_enabled` / `real_name_required_for_recharge` are enforced under `cn` only; under other profiles they may be switched off in prod, and a switched-off CAPTCHA is a configuration warning rather than a boot failure. `admin_mfa_enabled` and `sms_provider≠mock` apply to every profile.
- Sensitive values are stored AES-256-GCM encrypted (`app/core/crypto.py`), AAD bound to the row's key name; the ciphertext carries a kid, and the encryption key is derived from the master key via HKDF.
- **The AAD is bound to the key name, so a direct UPDATE of a row's key destroys the ciphertext**: renaming a secret key needs a migration that decrypts under the old key and re-encrypts under the new one (or operators re-enter the value).
- The master key `SUPERDL_CONFIG_ENCRYPTION_KEY` comes only from env and is required in prod (fail-fast); rotation uses the dual-key read migration through `SUPERDL_CONFIG_ENCRYPTION_KEY_PREVIOUS` (see [../../deploy/cluster/runbooks/key-rotation.md](../../deploy/cluster/runbooks/key-rotation.md)).
- Read endpoints return only the configuration state and a last-4 preview; the audit detail records only key names and the reason.
- Credentials are not handed to ops: the three platform-config endpoints are `admin` only; when ops generate an enrollment command the server reads on their behalf.
- Not in the configuration centre: `payment_mock`, `sms_provider≠mock` / `email_provider≠mock` in prod, and infrastructure settings such as JWT / DB / domains stay env-only with their prod fail-fast checks; the write side refuses `sms_provider=mock` / `email_provider=mock` in prod (`prod_forbidden`). The environment-independent invariant `real_name_required_for_recharge=true ⇒ real_name_enabled=true` (`_check_real_name_invariant`, the same rule as `Settings._validate_invariants`).
- Channel factories read the effective configuration asynchronously: `get_channel(name, session)` / `get_sms_channel(session)` / `get_email_channel(session)` / `get_realname_provider(session)`; WeChat and Alipay channel instances are cached by configuration fingerprint. The SMS protocol is kind-based (`send(phone, "verify" | "notice", params, locale=…)`): Aliyun maps the kind to its template code internally, Twilio renders the body from `app/core/verification/templates.py` (en-US / zh-CN).
- Filing numbers are delivered at runtime through `site-config`, not baked into build-time env.
