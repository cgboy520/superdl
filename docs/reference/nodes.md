# Nodes and cluster

One-command node enrollment, node inventory and cluster capability probing. Module `app/modules/nodes/`.

## Data model

- `node_enrollments`: token_hash (sha256, unique), progress_token_hash? (sha256, unique, issued at the first bootstrap), pool (kata/hami/mig/cpu), hostname?, note?, nvme_devices JSONB?, status, phase, error, node_name, reported_ip, os_info JSONB, gpu_info JSONB, expires_at (default 24 h, 1–168 h, absolute deadline), last_report_at, joined_at, created_by, idempotency_key (unique together with created_by)
- `node_specs`: node_name unique, pool_label?, unlabeled, gpu_model_raw?, gpu_model? (canonical), label_synced, gpu_count, gpu_used, vram_gb, vcpu, mem_gb, disk_gb, driver_version?, cuda_version?, status (Ready/NotReady/Cordoned/Missing), last_seen; two desired-state columns written by the admin API and converged by handlers and the patrol: `desired_unschedulable` (cordon) and `desired_pool` (pool switch)
- `cluster_status`: single row id=1, api_reachable, k8s_version?, distro? (rke2/k3s), hami_ready, dcgm_present, kps_present, gpu_operator_present, kata_runtimeclass, nvidia_runtimeclass, gateway_ready, cert_manager_ready, nodes_ready, nodes_total, storage_classes JSONB?, pools JSONB?, pools_ready JSONB? (pool → number of Ready and schedulable nodes), component_facts JSONB? (health-check key → state / headline number / fact rows / object table), error?, probed_at. The boolean columns are the criteria of the dispatch gate; `component_facts` feeds the health panel on the cluster page; neither replaces the other

Install state machine: pending → installing → rebooting ⇆ installing → joining → joined, with the side terminal states failed / expired / revoked (any non-terminal state can fall to expired on the absolute deadline). The terminal states joined / failed / expired have one more edge to revoked, **reachable only through node decommissioning** (a manual `revoke_enrollment` on a terminal state is 409).

## Rules and invariants

### Tokens

- Tokens are `sdln_`-prefixed 256-bit random strings, only the sha256 is stored; invalid / expired / revoked / terminal → 404. Progress tokens have the `sdlp_` prefix and the same shape.
- Tokens never enter the URL or the command line: the generated command writes the token to `/run/superdl-join.token` (0600) via stdin and the script only accepts `--token-file`; curl always injects the Authorization header through `--config`. The cluster server URL and join token are not in the script; the script exchanges the token for them via `POST /bootstrap`.
- The enrollment token is one-off: the first bootstrap (pending→installing) consumes it and issues the narrow progress token (only `/progress`; invalidated together with regenerate, revoke and enrollment-token rotation); script re-runs and resume-after-reboot use only the progress token on disk.
- Absolute token expiry: expires_at applies to every non-terminal state (progress only refreshes last_report_at); once expired, 404; the reconciler sweeps rows into expired.
- The expected hostname is required when issuing a token; a bootstrap reporting a different hostname sets failed and returns 409.
- The configuration handed out by bootstrap is narrowed to 9 keys (cluster group server_url / join_token / agent_version / driver_version / install_mirror / registries_yaml + registry group registry_host / registry_ca_pem / registry_proxy_projects); the full effective configuration never leaves through the enrollment path.
- One token per node, no reusable batch tokens; no drain. The join token lands in the node's agent config file (0600 root); rotation is described in the server token / agent token section of `deploy/cluster/README.md`.
- Bootstrap consumes the enrollment token under a `SELECT … FOR UPDATE` row lock: of concurrent bootstraps with the same token only one moves to installing, the others see the consumed state and get 404.

### Inventory and patrol

- The reconciler (30 s, advisory lock 1009) decides joined: the node_name appears in K8s and is Ready → the platform applies the pool's full label set → only a successful write moves the row to `joined` (two phases: the transaction only collects work, K8s writes happen outside it in an independent try per node; a failed write leaves the state unchanged for the next round). Nodes still installing are unlabeled, so the reconciler lists nodes with `include_unlabeled`. No heartbeat for 2 h → failed. Reads use `FOR UPDATE SKIP LOCKED`.
- The node patrol (60 s, advisory lock 1010) is the source of truth for nodes: phase A pure K8s read → B single-transaction DB convergence → B2 unenrolled isolation → C model label convergence → C2 pool label correction → D cordon desired-state convergence (C / C2 / D are independent tries per node). `enrollment.gpu_info` is only the one-off install snapshot.
- **The pool label key is `node-restriction.kubernetes.io/superdl-pool`** (`core/k8s/base.POOL_NODE_LABEL`): the prefix is protected by the NodeRestriction admission plugin, so a kubelet cannot set it via `--node-label`; only the platform SA can write it through the allow-list of admission policy ③. The old key `superdl.io/pool` (`LEGACY_POOL_NODE_LABEL`) is always "delete" in the desired set of `pool_node_labels` and is removed by reconciliation / pool switch / C2.
- **Unenrolled isolation (phase B2)**: a non-infra node (without `node-restriction.kubernetes.io/superdl-infra` or `node-role.kubernetes.io/{control-plane,master,etcd}`) with no `node_enrollments` row in any status, no `desired_pool` in the inventory and no pool label → goes through `service.request_cordon` (desired state to the inventory + outbox, the same path as a manual admin cordon, not repeated once requested) and logs a `node_unenrolled` error every round; the standing gauge `superdl_node_unenrolled` is reset each round to the number of such nodes (consumer `NodeUnenrolledJoined`). A node with a pool label but no enrollment row is not isolated, it only gets a `node_pool_label_without_enrollment` warning. Once the origin is verified, ops decommission it or add the enrollment.
- **The source of truth for pool label convergence (phase C2) is the desired pool, priority `node_specs.desired_pool` > enrollment**; the enrollment side considers both joined and failed rows, and with several enrollments under one hostname the row with the largest id wins. Spec snapshots (model / VRAM / driver / CUDA) only come from joined rows. **Both missing and mismatching labels are fixed by C2** (after a Node object is deleted and recreated the kubelet re-registers without the pool label, i.e. unlabeled).
- **C2 applies the pool's complete label set** (`core/gpu_adapter.pool_node_labels`): pool label + the new pool's GPU operand labels + **mandatory deletion of the old pool's leftover keys** (gpu-operator does not overwrite existing values when deriving `nvidia.com/gpu.deploy.*`). The platform SA's write permission comes from the named allow-list of admission policy ③.
- Correction order is **cordon first, then labels**; the cordon goes through `service.request_cordon` (desired state to the inventory + outbox), the same path as a manual admin cordon, and phase D re-converges by desired state.
- `superdl_node_pool_label_mismatch_total` increments on **detection**, not after a successful correction. Consumer `NodePoolLabelMismatch` (critical). The criterion is "label mismatch **and** node still schedulable". Unlabeled nodes do not count.
- **Pool switching** (`switch_node_pool`) only between the `kata` / `hami` / `mig` pools; the `cpu` pool is the physical property of GPU-less machines and does not take part. Gates in order: node in the inventory → target pool valid and different from the current one → current pool not cpu, and `gpu_count > 0` **or** the node is already in one of kata / hami / mig (when the target pool's components fail to start the observed card count drops to 0, so the node must keep a way back) → switching to mig requires `core/gpu_models.supports_mig`, switching to kata requires `core/gpu_models.supports_passthrough` (both tables fail closed, unrecognised models are always rejected; `supports_mig` / `supports_passthrough` on `GET /api/admin/v1/nodes` are these two predicates and the admin pool-switch modal only reads them, it holds no family table of its own) → **zero unreleased instances on the node** → target pool runtime ready (`require_pool_runtime`). The transaction does exactly two things: write `desired_unschedulable=True` and `desired_pool`, enqueue `node.switch_pool`.
- **A pool switch needs no node-side action and no reboot (except for the kata pool, see below)**: every node-side software difference between pools is delivered by DaemonSets keyed on labels (`kata-deploy` follows `node-restriction.kubernetes.io/superdl-pool=kata`, the HAMi device plugin follows `node-restriction.kubernetes.io/superdl-pool=hami`, gpu-operator's vfio-manager and sandbox plugins follow the `gpu.deploy.*` labels it derives from `workload.config`), and whole-card passthrough binding / unbinding is done by vfio-manager at runtime (`vfio-manage bind --all` on start, `vfio-manage unbind --all` in preStop). **IOMMU is part of the install baseline and does not change with the pool** (see "Configuration and installation").
- Platform-specific hardware limits (Grace GB10 / GB200 cannot be passed through, unified memory, no GRUB argument on aarch64, x86 IOMMU argument by vendor) are collected in `deploy/cluster/runbooks/hardware-notes.md`.
- **The kata pool requires a host without the NVIDIA driver**: gpu-operator's vfio-manager exits with `fatal: driver is pre-installed on host` when it sees a preinstalled driver, the GPU stays on the `nvidia` driver and cannot bind to `vfio-pci`, the sandbox-validator goes into CrashLoopBackOff and the node's allocatable `nvidia.com/gpu` drops to 0. `node-join.sh` skips the driver and container-toolkit for the kata pool and fails the driver phase when a host driver is detected; moving an in-service node with a driver installed into kata requires uninstalling the driver and rebooting first, steps in [node-pool-switch.md](../../deploy/cluster/runbooks/node-pool-switch.md). **The whole-card passthrough model list is `core/gpu_models.PASSTHROUGH_CAPABLE_FAMILIES`**: the integrated GPUs of Grace superchips (GB10 / GB200) have firmware-enforced 1:1 IOMMU mappings, the kernel refuses to bind them to vfio-pci, and they are not on the list.
- **"Unreleased instance" means `status != released`, including stopped / frozen / failed** (`orchestrator/queries.count_active_instances_on_node`); the instance disk is a node-local LV and start-up pins the instance back to its node. Pool switch and decommission share this gate; decommission additionally has the `force` bypass (for machines that cannot be recovered).
- **A non-null `desired_pool` overrides the enrollment and is not cleared after the switch**: after a Node object is recreated, C2 restores the labels from it.
- **Pool labels are written only by the platform**: `node-join.sh` writes no pool label (the agent config carries no `node-label`); the node registers unlabeled, the reconciler applies the full label set when it judges Ready, and only a successful write moves the row to `joined` (a failure does not advance the state, the next round retries).
- **A pool switch does not uncordon automatically**: the handler stops at "labels converged"; after verifying the components landed, ops uncordon manually. Steps in [node-pool-switch.md](../../deploy/cluster/runbooks/node-pool-switch.md).
- **Node decommissioning** (`decommission_node`) does three things in one transaction: cordon desired state to the inventory → every enrollment under that hostname set to revoked → enqueue `node.decommission` so the worker deletes the Node object. Two boundaries the platform cannot manage go back to ops (the admin decommission dialog says so): deleting the Node object **does not revoke the kubelet certificate** (a live kubelet re-registers, and the patrol cordons it again by desired state); join token rotation and kubelet certificate revocation are control-plane actions.
- **Which nodes may be deleted is decided by the admission layer, not by RBAC**: `deploy/cluster/admission/tenant-restrictions.yaml` policy ⑦; nodes with control-plane / etcd roles or the infra placement label cannot be deleted. After a control-plane Node object is deleted the kubelet re-registers, but `node-restriction.kubernetes.io/superdl-infra` does not come back with it.
- Business code reads the inventory and never calls K8s live; a vanished node is first set to `Missing` and its row is deleted only after the retention period (see [limits.md](./limits.md)); listing validation only accepts Ready.
- The patrol calls K8s directly from the worker convergence loop with idempotent retries; the outbox only covers business transactions on the request path.
- Model normalisation is in `core/gpu_models.py`: `canonical_gpu_model(raw)` returns None for unrecognised models and appends `-{n}G` to families with several capacities under one name (A100/A800/H100/H800/H200/V100); `model_matches(sku, node)` is equality or a prefix match on the node value. The CMP series is recognised as `CMP<digits>HX`: when nvidia-smi only reports a generic name, the bootstrap-reported name falls back to the model in lspci's square brackets, VRAM still comes from nvidia-smi.
- `gpu_model` takes part in scheduling through the platform's own label `superdl.io/gpu-model` written back to the node. The **physical card count** of the hami pool relies on the GFD label `nvidia.com/gpu.count` (missing label → managed as 0); GFD for both tiers ships with gpu-operator.
- Inventory `driver_version` / `cuda_version` follow the GFD labels `nvidia.com/cuda.{driver,runtime}-version.full` (assembled from `.major/.minor/.revision` when missing); the `os_info` reported at install time is only the fallback without GFD.

### Cluster capabilities

- The cluster page runs ten component health checks: node readiness / HAMi / gpu-operator / DCGM / RuntimeClass nvidia / RuntimeClass kata-qemu / storage classes / instance ingress (key `gateway`) / certificate issuance / monitoring stack.
- **Five health states**: `ok` all ready / `degraded` partially ready / `down` missing or all down / `disabled` component present but the capability is off / `unknown` snapshot untrustworthy. The decision logic is centralised in `app/core/k8s/health.py`, shared by real and fake.
- **Readiness looks at ready counts, not at object existence**: `gpu_operator` takes `numberReady == desiredNumberScheduled` for every operand DaemonSet in the gpu-operator namespace, `dcgm` the same ratio for the dcgm-exporter DaemonSet, `monitoring` the ready replicas of the Prometheus StatefulSet.
- **The `unknown` window and the dispatch gate share one source**: `probed_at` older than `HAMI_GATE_MAX_AGE` (10 minutes) or `api_reachable` false → all ten checks are `unknown`, the last facts are still returned for reference. Never probed (no cached row) additionally yields the install commands; merely stale does not.
- **The pool node count of `kata_runtimeclass` only counts Ready and schedulable nodes**: RuntimeClass present but no Ready node in the pool → `disabled`. Inventory and sellability are not part of the health checks; see `pools_ready`.
- `storage` checks by name for `topolvm-provisioner` (mandatory, missing → `down`) and `superdl-cephfs` (optional, missing only marks the data-disk fact as warn).
- `gateway` judges each listener separately: overall `Programmed=True` but one listener not ready → `degraded`; the object table shows port / protocol / attachedRoutes / condition reason, the same criteria as the north-south ingress checklist in `deploy/cluster/runbooks/cluster-validation.md`.
- **All component copy is mapped from keys to the locales of both consoles**; the backend emits facts only; `fix_hint` (repair command, only for `down` / `degraded` / never probed) and `diag_hint` (first troubleshooting step, always given) are commands and do not vary by language.
- Prometheus-side facts (DCGM sample freshness, scrape target health, firing alert count) are fetched by the patrol through `metering/service.py` and merged into the snapshot; the cluster page stays a pure DB read; an unavailable Prometheus only drops a few facts and changes no component state.
- **The live deep probe** answers the "why not ready" the snapshot cannot: phase / node / stuck reason (ImagePullBackOff etc., from the waiting/terminated containerStatuses) / restart count of the matching Pods, Warning events of the unready objects; the `nodes` item adds pressure conditions and taints of non-Ready nodes, the `cert_manager` item adds certificate Ready and expiry (CRD not installed is treated as no certificates). It is the second read-only exception for direct K8s access on the request path, constraints in [decisions.md](../decisions.md); the deep probe only adds live detail, never changes component states, and on failure the frontend degrades to showing the snapshot only.
- **The instance-ingress criterion is `Programmed=True` in `status.conditions` of the `Gateway superdl` object**, not a ready controller Deployment. CRD not installed or object not applied are both 404, counted as "not ready" without recording `error`. The probe needs get/list on `gateway.networking.k8s.io/gateways` (node-mgr role in `deploy/app/k8s/01-rbac.yaml`).
- The HAMi gate has no scheduling fallback: shared-tier capability not ready → `CLUSTER_NOT_READY` straight away, schedulerName is pinned statically. The dedicated tier looks at RuntimeClass `kata-qemu` (`require_kata_runtimeclass`). The gate criteria share their source with `build_gpu_request`: **first whether a card is needed, then which pool**; an instance with `gpu_count == 0` requests no `nvidia.com/*`, has an empty `schedulerName` and only passes the StorageClass check.
- The distribution has no runtime configuration; the platform derives it from the probed gitVersion (`+k3s` / `+rke2`); both tiers install the same component set, differing only in `deploy/cluster/values/light/`. Tier availability depends on Ready nodes in the pool and the runtime being in place.
- k3s only probes the nvidia runtime and sets no default runtime; shared-tier tenant Pods set `runtimeClassName: nvidia` explicitly; with RKE2 + gpu-operator the default runtime is already nvidia, so it stays None.

### Configuration and installation

- Cluster configuration group keys: `cluster_server_url` / `cluster_join_token` (secret) / `cluster_agent_version` / `node_driver_version` / `node_registries_yaml` (empty = platform-generated; must not contain credentials) / `node_install_mirror` (`official` | `cn`, default `official`).
- **`cluster_join_token` only accepts an agent token** (the `agent-token` value of the server config): the server node-token form `K10<64hex>::server:<pw>` would make a GPU node join as a server; the configuration center (`SETTING_SPECS` negative lookahead) and `node-join.sh` both reject it before writing the agent config.
- Cluster keys are not fail-fast at boot: the lifespan checks the effective configuration once the DB is ready and logs an error + the cluster page shows a red card + creating an enrollment command returns 409.
- `render_registries_yaml` (the default when `node_registries_yaml` is empty) generates from the registry group: Spegel `"*"` + one upstream mirror per `registry_proxy_projects` entry rewritten to the Harbor proxy-cache project + `configs.<host>.tls.ca_file` when `registry_ca_pem` is non-empty (the `__RANCHER_DIR__` placeholder is replaced by node-join with the distribution's directory and lands as `harbor-ca.crt` 0644); no auth. The same file for server nodes is distributed by ansible from `deploy/cluster/rke2/registries.yaml`.
- Pool labels and the GPU Operator operand placement labels **are written by the platform, node-join never touches them** (the agent `config.yaml` has only server and token). The complete desired set is in `core/gpu_adapter.pool_node_labels`: kata pool `workload.config=vm-passthrough` and delete `deploy.device-plugin`, hami pool `deploy.device-plugin=false` and delete `workload.config`, mig and cpu pools delete both keys. Leftover keys of the old pool must be deleted; gpu-operator does not overwrite existing values when deriving `gpu.deploy.*`.
- **IOMMU is enabled at install time for every GPU pool without branching by pool**: x86_64 derives the argument on every run from the CPU vendor (`/proc/cpuinfo` `vendor_id`: GenuineIntel → `intel_iommu=on iommu=pt`, AuthenticAMD / HygonGenuine → `amd_iommu=on iommu=pt`, other vendors fail closed and can be set explicitly with `SUPERDL_JOIN_IOMMU_ARGS`) and rewrites the managed `/etc/default/grub.d/99-superdl.cfg` plus `update-grub` only when its content differs, aarch64 writes nothing; the criterion is always a non-empty `/sys/kernel/iommu_groups`, empty requires one reboot; the cpu pool skips it.
- **kata pool installs skip the host driver chain**: the driver and nvidia_toolkit phases of `node-join.sh` are skipped for the kata pool (whole-card passthrough is taken over by vfio-pci, the host runs no GPU containers); an already installed host driver fails the driver phase so the node does not join in a broken state. The nouveau blocklist and IOMMU are done as usual.
- **cpu pool = GPU-less machines**, hosting pure CPU instances (`tier=cpu`, see [catalog.md](./catalog.md)). The whole NVIDIA chain is skipped at install time: no NVIDIA detection, no nouveau blocklist, no driver or container-toolkit, no driver / CUDA version report, no NVIDIA operand labels. The other steps are the same as for GPU nodes.
- **The installer source defaults to official**: `node_install_mirror` defaults to `official` (get.k3s.io / get.rke2.io), `cn` (rancher-mirror.rancher.cn) is enabled on demand under "Platform configuration · Cluster access"; the `install_mirror` handed out by bootstrap accepts only these two values, any other value (including empty) fails closed in the agent_install phase. Each source has its own set of built-in sha256 pins (neither installer carries a version number); a mismatch aborts and prints the expected / actual digest plus the refresh command. Upgrade note: mainland-China deployments that relied on the previous default must set `node_install_mirror` to `cn` explicitly, otherwise new nodes download from the official source.
- **The distribution baseline is the Debian family**: precheck reads `/etc/os-release` and only passes `ID` ubuntu / debian or `ID_LIKE` containing debian (every later step is apt / dpkg / update-initramfs / update-grub); other distributions fail closed.
- `node-join.sh` ships with the API image; step markers make it re-runnable indefinitely; scenarios that need a reboot resume through a systemd oneshot. Phase names: bootstrap/precheck/nouveau/sysctl/iommu/driver/nvidia_toolkit/nvme_vg/reboot/registries/agent_config/agent_install/agent_start/waiting_node.
- **Running node-join on the server itself (light single-node)**: the criterion is a running local `k3s.service` / `rke2-server.service`; then no agent `config.yaml` is written and no agent is installed or started, pool labels are applied to the node object through the local kubectl (`k3s kubectl` / `/var/lib/rancher/rke2/bin/kubectl`); the server service is restarted after the toolkit is installed; `--uninstall` does not run the distribution's uninstall script and does not delete the server's config / registries.
