# Orchestration

Instance state machine, outbox orchestration, reconciler, access (SSH / JupyterLab) and the K8s abstraction.

## Data model

- `instances`: uuid, user_id, SKU snapshot (sku_id + `spec` jsonb + price_hourly; `spec.base_price_hourly` is the SKU's **list price** snapshot, used to restore the price on spot → on-demand conversion), market (CHECK ∈ {on_demand, spot, subscription}, default on_demand), gpu_count (CHECK ≥0; **0 = pure CPU instance**, see [catalog.md](./catalog.md)), status, k8s (namespace / node_name(253)), ssh_port?, jupyter_token (AES-GCM ciphertext), image_ref, data_disk_id?, workload_type (CHECK ∈ {dev, service}, true exactly when service_id is set), service_id? / service_revision? / service_slug? / service_port? / health_path? (owning online service and the exposure spec snapshot of that revision), with_ssh, container_command? / container_args? (jsonb), env_encrypted?, idempotency_key unique? (24 h window), version (optimistic lock)
- `instance_events`: instance_id, from_status, to_status, reason, actor (user/system/admin), metadata — append-only, the primary basis for billing
- `port_allocations`: port unique (30000–32767), instance_id nullable (partial unique: at most one port per instance)
- The relation between online services (`services`, `service_api_keys`) and their revision instances is in [services.md](./services.md)

State machine: creating→running/failed/releasing; running→stopping/failed; stopping→stopped/releasing; stopped→starting/frozen/releasing; starting→running/failed; frozen→stopped/releasing; failed→stopped/releasing; releasing→released (the only terminal state). The running↔non-running edges are the billing edges. failed→stopped is the fault-recovery edge (restart on the existing instance disk); stopping→releasing is the give-up-on-stuck edge. Subscription expiry adds no state or edge, only two more reasons: arrears `arrears_stop` / `arrears_freeze`, expiry `subscription_expired` / `subscription_freeze`.

## Rules and invariants

- State transitions go only through the transition functions in `orchestrator/service.py` (which write `instance_events` in the same transaction); an illegal transition is `INSTANCE_INVALID_TRANSITION`.
- The lifecycle has two layers: `create_instance_row` / `stop_instance_row` / `start_instance_row` / `release_instance_row` are the non-committing row-level core (the services module calls them inside its own transaction); the user-facing entry points such as `create_instance` only fetch the instance and commit. `create_instance_row`'s `service=ServiceBinding(...)` builds the instance as a revision of an online service; `exclude_instance_id` lets the old instance about to be replaced stop counting against quotas and soft admission (balance is not exempted). Lock order instance → service → disk → wallet.
- The request path never calls K8s: business writes and `outbox_tasks` share one transaction. There are two read-only exceptions, both fenced by rate limit / timeout / failure degradation: the instance log endpoint (plus an owner check) and the live deep probe of the admin component health check (`GET /api/admin/v1/cluster/components/{key}/probe`, see [nodes.md](./nodes.md)).
- **Purchase-mode changes do not write `instance_events`** (`subscribe_instance` and `convert_to_on_demand`); their trace is in the audit log and the ledger.
- K8s access is concentrated in `app/core/k8s`; the `K8sOrchestrator` protocol is the only interface (`app/core/k8s/base.py`). FakeOrchestrator and RealOrchestrator implement every protocol method synchronously.
- RealOrchestrator per tenant: a dedicated namespace (PSA enforce=baseline + audit=restricted), a ResourceQuota safety net, an egress-isolating NetworkPolicy; data disks are one PVC each, created / grown by `disk.provision` and deleted by `disk.deprovision` (idempotent + backoff, no Job). Existing ns / NetPol / Quota objects are patched into shape; K8s lists are always paginated (limit=500 + continue), synchronous calls run on a dedicated bounded executor. Object construction is pure (`build_instance_pod` / `build_prewarm_job`); `scripts/render_admission_probes.py` renders them into manifests that CI checks against the admission policies with `--dry-run=server`.
- Image pull credentials never land on nodes or in plaintext in the Pod spec: before creating a Pod the outbox calls `core/k8s.ensure_registry_pull_secret` right after `ensure_namespace`, which manages `superdl-registry-pull` in the tenant ns (skipped when the annotation fingerprint matches), and the Pod spec references it via `imagePullSecrets`; without a robot account `image_pull_secret=None`. Prewarm Jobs use the same chain.
- Ports are allocated from the `port_allocations` pool and returned on release / failure (not on stop); an exhausted pool fails creation with an explicit error; the level is refreshed every reconciler round into `superdl_ssh_port_pool_ports{state}`.
- Per-user instance count, GPU count and CPU-instance vCPU count are three disjoint dimensions; values in [limits.md](./limits.md).
- Releasing an instance triggers the disk wipe task; data disks are independent, see [disks.md](./disks.md).

### Spec and scheduling

- gpu_adapter produces the resource request syntax **per pool** (HAMi `nvidia.com/gpu` + `gpucores` / `gpumem`; MIG profile; whole card), picks the RuntimeClass (kata-qemu / runc), emits the `superdl.io/gpu-model` nodeSelector from the canonical model, and passes through `annotations` (`nvidia.com/use-gputype`, switch `SUPERDL_HAMI_USE_GPUTYPE`, default off).
- **The `gpu_count == 0` decision comes before the pool branch**: empty resource request, no model pin, `runtimeClass=None`, `hostUsers=false`, nodeSelector only carries the pool label.
- Pod spec multipliers: GPU instances scale vCPU / memory by card count, CPU instances always use 1; the system disk is not scaled.
- The valid `gpu_count` range at creation follows the SKU form: `max_gpus_per_instance == 0` accepts only 0 (else `orchestrator.cpuSkuNoGpu`), otherwise `1..max` (else `orchestrator.gpuCountRange`). The contract layer says `ge=0, le=8`; the pairing gate is in the service.
- The model nodeSelector comes from the `gpu_model_selector` key of the spec snapshot (None for unrecognised models).
- The create / start / restart entry points read the cluster capability cache as a gate; not ready → `CLUSTER_NOT_READY`; the criteria share their source with `build_gpu_request`, see [nodes.md](./nodes.md).

### Reconciler and retention

- The reconciler (30 s, advisory lock) is the only convergence point: Pod Ready while DB says creating/starting → running; Pod gone while DB says running → failed; Pod present while DB is terminal → force delete; creating longer than 5 min → failed (a first creating timeout that is the platform's fault refunds the subscription prepayment and wipes the instance disk in the same transaction; for service instances with a non-empty `health_path` whose workspace container has started (`PodStatus.started_at`) the timeout is the tenant's fault: the failure edge carries `metadata.occupied_since`, the occupancy is billed, no refund, no wipe, see [billing.md](./billing.md)). One `list_instance_pods` per round is the status source; no per-instance `get_status`.
- Stuck stopping/releasing have two timeout levels (`stopping_timeout_seconds` / `releasing_timeout_seconds`): the first re-sends the delete via the outbox, the second force-deletes and then converges along the normal edges. Stuck instance count in `superdl_reconcile_stuck_instances`.
- Leak reclamation circuit breaker: when the share of unknown Pods exceeds `leak_reclaim_abort_ratio` the round aborts and counts `superdl_reconcile_leak_aborted_total`; in-flight deletions get the same two-level grace, everything else is force-deleted.
- Retention GC runs inside the reconciler: failed longer than `failed_retention_days` → notify and move to releasing; stopped longer than `stopped_retention_days` → move to releasing, with a warning `stopped_retention_warn_days` ahead. Data disks are unaffected. Thresholds in [limits.md](./limits.md).
- Node-loss detection looks at node readiness first (`list_nodes`): not-ready longer than `running_unready_timeout_seconds` with the node NotReady / unknown → node_lost (user notified); node healthy → pod_unready. **`workload_type='service'` skips the pod_unready branch** and the instance stays running; `pod_lost` and `node_lost` are not exempted.
- **`instances.unready_since` accumulates across rounds and is reset in exactly two places**: any path entering running, and "the Pod was observed ready again this round". The grace period and the `pod_unready` exemption of service instances return "no loss reason" but **must not** reset it. It is also the source of the event's `metadata.unready_since`, from which the billing cut-off for platform-fault loss is computed (see [billing.md](./billing.md)).

### Purchase modes

Three purchase modes (`instances.market`), orthogonal to `skus.tier`: one SKU, three ways to sell it.

| Value          | Meaning                                                                                                                                                                                                                                             |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `on_demand`    | Pay as you go, into `bills_hourly`                                                                                                                                                                                                                  |
| `subscription` | Prepaid period, charged once at order time; hourly settlement skips it in one place, `billing_candidates` (see [billing.md](./billing.md))                                                                                                          |
| `spot`         | Spot (on-demand price × `spot_discount_pct`), **may be reclaimed by the platform** when capacity is tight. Same billing chain as on-demand, the discount only lands in `price_hourly`. Requires SKU `spot_enabled` (see [catalog.md](./catalog.md)) |

- `market` is fixed at creation; **only two paths change it**: `subscribe_instance` (on-demand → subscription) and `convert_to_on_demand` (spot → on-demand). Subscription → on-demand and on-demand → spot are not offered.
- **`instances.price_hourly` is the effective hourly price under that purchase mode**, computed in one place by `price_for` in `app/core/pricing.py`. Market quotes, creation estimates and renewal quotes share the same functions.
- **The start gate of a subscription instance looks at the period, not the balance**: `start` with `market='subscription'` goes through `assert_subscription_active` (expired → `SUBSCRIPTION_EXPIRED` 409), not `assert_can_afford`. A missing subscription row counts as expired.
- **An unexpired subscription instance keeps occupying soft-admission stock even when stopped.** `_reserved_slots` counts "stopped / frozen and still covered" instances on the same SKU as occupied. **Reserved at the control-plane level, not physically**; the create page and the renewal entry say so to the user. Only the same SKU counts.
- Renewal refreshes `instances.price_hourly` in the same transaction; renewing a frozen instance returns it to `stopped` and clears `frozen_deadline`, without starting it.
- **On-demand → subscription "settles first, then flips"**: `subscribe_instance` settles the on-demand stretch before the conversion under the wallet row lock (at the **pre-conversion** on-demand price), then writes the subscription row, flips `market` and refreshes `price_hourly`. Details in [billing.md](./billing.md).
- **The idempotent replay is checked before every guard.**
- Both conversion paths accept running / stopped only.
- The subscription summary in list and detail (`InstanceOut.subscription`: period / period_count / expires_at / status / auto_renew / amount_paid) and the service endpoint slug are back-filled by `attach_instance_details` with **one batch query each** (see [web.md](./web.md)); the admin console uses the same path.

### Spot preemption

Selector and reclamation are in `app/modules/orchestrator/preempt.py`, triggered from soft admission `_soft_admit_capacity`; cases in `apps/api/tests/test_spot.py`. The money side is in [billing.md](./billing.md).

Three hard rules are written verbatim in the spot consent modal (see [../ui-ux-spec.md](../ui-ux-spec.md) §1 rule 5); **changing the code means changing the copy, both in one commit**:

1. **Select only within the same pool and model.** Candidate predicate `status='running' AND market='spot' AND spec->>'pool_label' = pool AND spec->>'gpu_model_selector' IS NOT DISTINCT FROM canonical model` (unrecognised models snapshot as NULL).
2. **Newest `created_at` first.** The only ordering (ties by `id` descending).
3. **If one machine's worth cannot be freed, nothing moves.** `gpu_count` is accumulated until enough; if not enough, the empty list is returned and the caller gets 409 `NO_CAPACITY`.

- Only **non-spot GPU-tier requests** trigger preemption.
- Gap conversion `cards_needed = ⌈missing slots ÷ sellable_per_gpu⌉`; "one instance frees `gpu_count` cards" uses the same approximation as soft admission's `_sku_free_capacity`.
- **Preemption runs in the same transaction as the caller's instance creation**; `preempt()` does not commit.
- Grace window: for each selected instance, three things in the same transaction — `transition(→ stopping, reason='preempted', actor='system')` + `enqueue('instance.stop', delay_seconds=spot_grace_seconds)` + SMS and in-app notification. **The state machine moves to `stopping` immediately**, **the Pod is deleted only when the window ends**. Terminal state `stopped`, the instance disk is kept.
- The notification dedup_key carries the instance id and the minute, **not bucketed by day**.
- The grace window shares a time budget with `creating_timeout_seconds`; the real upper bound of `spot_grace_seconds` is in [limits.md](./limits.md).
- Each reclaimed instance counts `superdl_spot_preempted_total` (see [observability.md](./observability.md)).
- The admin `/preempt` **does not reuse force-stop**; the reasons are separate.
- Conversion to on-demand **touches no Pod, zero interruption**: the price is restored to `spec.base_price_hourly`, **never derived back from the discounted price**; the current clock hour is settled entirely at the on-demand price (see [billing.md](./billing.md); this must be in the conversion confirmation dialog); `assert_can_afford` runs once more after the conversion.

### Instance forms

Two forms (`instances.workload_type`); they differ only in the `build_pod_spec` branch and in which K8s objects are created; state machine, billing, quotas, reclamation, reconciler, monitoring and audit are all shared. A `service` instance is one revision of an online service (`service_id` points back), with the exposure spec (`service_slug` / `service_port` / `health_path`) snapshotted on the instance row:

|                             | `dev` (SSH + JupyterLab) | `service` (revision of an online service)                                                                                                          |
| --------------------------- | ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `restartPolicy`             | `Never`                  | `Always` (the kubelet restarts the container in place, the Pod is not recreated; Pod name = instance uuid)                                         |
| command / args              | not set                  | user-overridable (`container_command` / `container_args`)                                                                                          |
| User env                    | none                     | `env_encrypted` (whole bundle AES-GCM, AAD bound to the instance uuid); secret entries referenced via a per-instance Secret with `secretKeyRef`    |
| SSH NodePort Service        | always                   | only with `with_ssh`; when false the instance **does not enter the port pool**                                                                     |
| Jupyter Service + HTTPRoute | always                   | not created                                                                                                                                        |
| Service Service + HTTPRoute | none                     | `<uuid>-svc` ClusterIP + an HTTPRoute attached to the `svc-https` listener                                                                         |
| Probes                      | none                     | with a non-empty `health_path`: startupProbe (threshold = `creating_timeout_seconds` // 10 − 1, total below the platform timeout) + readinessProbe |

Domain rules, auth chain, status derivation and API key lifecycle of online services are in [services.md](./services.md).

### Gateway and access

- **Service routes may only attach to the `svc-https` listener**: `app-https` has no `SecurityPolicy.extAuth`; a route attached there still works, unauthenticated, without any error. Both listener names are pinned in `core/k8s/base.py` as `GATEWAY_APP_LISTENER` / `GATEWAY_SVC_LISTENER`; the offline cases in `tests/test_k8s_real_units.py::TestServiceWorkloadObjects` assert them one by one.
- **The attachment contract of tenant HTTPRoutes** is pinned by three constants in `core/k8s/base.py` (`GATEWAY_NAMESPACE` / `GATEWAY_NAME` / `GATEWAY_APP_LISTENER`, which must match `deploy/app/k8s/04-gateway.yaml` verbatim; there is no `SUPERDL_*` setting for them): the route lives in the **tenant ns**, `parentRefs` points at `Gateway superdl` in the platform ns, `sectionName` is pinned to `app-https`. Cross-namespace attachment is authorised by the listener's `allowedRoutes.namespaces.from: Selector`, whose selector is the `superdl.io/managed=true` label that `ensure_namespace` puts on tenant namespaces; **no ReferenceGrant is needed**. Getting any of the three names wrong raises no error: `create` returns 201 and the route sits at `Accepted=False` / `NotAllowedByListeners` in `status.parents[].conditions`. Without `sectionName` the route attaches to every listener on the same port.
- **Jupyter's WebSocket and SSE rely on the gateway's `streamIdleTimeout: 1h`** (`ClientTrafficPolicy superdl-gateway`); when adjusting gateway policies do not fall back to the default 5 minutes.
- **Route count is a capacity variable**: one HTTPRoute per instance, and both the data plane and the EG control plane grow in memory with the route count. The light tier must either give the `EnvoyProxy` enough memory limit or cap the number of instances per machine, see `deploy/app/k8s/04-gateway.yaml`.
- Orphan endpoint cleanup LISTs cluster-wide by the `superdl.io/managed` label (Services and HTTPRoutes); HTTPRoute has no typed model, so it goes through `CustomObjectsApi` with raw dicts, the pagination cursor being `metadata.continue`.
- SSH is key-only; connection string `ssh root@<instance domain> -p 3xxxx`: the hostname is the instance's own domain (the same as Jupyter's, `orchestrator/service.jupyter_host`), distinguished by NodePort. Deployment constraint: the address the wildcard domain resolves to must forward both 80/443 and the `ssh_port_range` port range.
- SSH depends on three capabilities of the tenant container (`SYS_CHROOT` / `SETUID` / `SETGID`, see [security.md](./security.md)) and on the entrypoint running `chmod g-w,o-w` on `/root` before starting sshd.
- SSH host keys persist on the instance disk (`/root/.ssh/host_keys`); jupyter is started by the entrypoint's supervisor loop (not PID 1), and only 5 consecutive immediate exits fail the Pod.
- JupyterLab has one HTTPRoute per instance routed by host; hostname = `SUPERDL_JUPYTER_HOST_PREFIX` (default empty) + uuid + `.` + `SUPERDL_JUPYTER_DOMAIN_SUFFIX`, assembled in one place by `orchestrator/service.jupyter_host`. When the first-level domain is shared with other traffic, use the prefix to tell them apart (e.g. `jupyter-<uuid>.<domain>`); Jupyter and service endpoints are then separated by port, and `SUPERDL_JUPYTER_URL_PORT` (default 443) puts the port into the entry URL and `JUPYTER_ALLOW_ORIGIN`, **affecting only the origin, not the HTTPRoute hostname or the SSH connection string**; both separation schemes are in the "Domain rules" section of [services.md](./services.md). Certificates come from the listener's `certificateRefs`.
- The Jupyter token is generated by the control plane, stored as AES-GCM ciphertext and injected as a Pod env; the access endpoint issues a one-off bootstrap ticket (HMAC key = the token itself, single use, 60 s), the in-image `/superdl-bootstrap` handler redeems it and sets a first-party cookie; the stock `?token=` login is the fallback channel. **The instance image must be released before the control plane.**
