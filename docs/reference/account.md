# Accounts

Email-primary accounts (phone optional, E.164), verification codes by email or SMS, JWT sessions, SSH keys, identity verification entry point.

## Data model

- `users`: `email` (lower-cased, unique when set, `email_verified_at`), `phone` (E.164, unique when set), password_hash (nullable), status (active/frozen/deleted), low_balance_warn_hours, token_version, KYC fields `kyc_status` / `kyc_name` / `kyc_identity_masked` / `kyc_identity_hmac` (keyed digest) / `kyc_provider` / `kyc_ref` / `kyc_verified_at`. At least one handle is set on a live account; both are NULL after deletion.
- `ssh_keys`: user_id, name, public_key, fingerprint (SHA256, unique)
- `verification_codes`: `channel` (email / sms), `target` (normalized handle), code_hash (keyed digest, domain `vcode|channel|target|purpose`), purpose (register / login / reset_password / bind_handle), expires_at, used_at (voided for any reason), consumed_at (successful check only), attempts
- `used_refresh_tokens`: jti (PK), expires_at, used_at

## Rules and invariants

- User and admin JWT audiences are isolated (`SUPERDL_JWT_USER_AUDIENCE` / `SUPERDL_JWT_ADMIN_AUDIENCE`, defaults `superdl:user` / `superdl:admin`; issuer `SUPERDL_JWT_ISSUER`, default `superdl`); a user token on the admin API is always 403.
- Refresh tokens are consumed once: the jti lands in `used_refresh_tokens`, a replay revokes every outstanding token of that user; re-consuming the same jti within 10 s is treated as a normal rotation and re-issues without revocation.
- Refresh tokens travel only in an HttpOnly cookie: prod name `__Host-superdl_refresh` (Secure + `path=/` + no Domain), non-prod `superdl_refresh`.
- `users.token_version` is the revocation gate; freezing a user bumps it as well. Every read-modify-write of `token_version` (password change / freeze / refresh-replay revocation / logout-all) holds a row lock (`with_for_update`).
- Login rate limiting has four buckets; the password path counts before bcrypt and decides afterwards (`core/loginguard.login_attempt`, atomic under concurrency): `user-login:{ip}:{handle}` and `user-login-acct:{handle}` reset on success, `user-login-ip:{ip}` refunds this attempt on success, `user-login-acct-daily:{handle}` counts failures only and does not gate admission (`handle` = `core/handles.ratelimit_key`, hashed beyond 48 chars); the code path counts failures only; registration, password reset, KYC and code sending have their own buckets. Counters live in PG (see [security.md](./security.md)), limits in [limits.md](./limits.md).
- Password rules live in one place, `core/security.PasswordStr` (≥ 12 characters, ≤ 72 UTF-8 bytes, the bcrypt cap), shared by the user and admin request bodies; violations are 422.
- A verification code is voided once `attempts` hits the cap (`used_at` set, `consumed_at` still empty). Send gate order (`account/verification.py`): per-target precheck bucket → CAPTCHA → per-IP bucket → per-target backoff (advisory lock on `kind:value`) → per-target daily cap → platform budget of the channel (`core/sms.ensure_sms_platform_quota` / `core/email.ensure_email_platform_quota`). Backoff: a send is refused while the latest code for the same target is younger than `SUPERDL_SMS_SEND_INTERVAL_SECONDS`; with N consecutive codes whose `consumed_at` is empty (including burnt and expired ones) the interval is × 2^(N-1) (exponent capped at 3), reported as `CODE_TOO_FREQUENT`. Codes are `CODE_INVALID` / `CODE_TOO_FREQUENT` / `CODE_SEND_FAILED` regardless of channel.
- A delivery failure (SMS or email) voids the stored code and returns 502.
- Handles: `core/handles.py` normalizes (email lower-cased; phone E.164 with separators stripped) and masks (`mask_handle`: `a***@domain`, `+86****1111`; malformed emails and phones shorter than 11 characters become `******`); bare national numbers are not accepted anywhere. Sign-up needs an email; a phone is bound at sign-up or later via `/me/handles/*`, and the compliance profile (`core/compliance.py`) decides whether it is required and which dial codes are allowed. Accounts that predate email handles keep logging in by phone; the console shows an add-your-email banner until they bind one.
- Public keys must be ssh-ed25519 / ssh-rsa / ecdsa-*; uniqueness is per (user_id, fingerprint), duplicates → `SSH_KEY_DUPLICATE`, invalid keys → `SSH_KEY_INVALID`; deletion is a hard delete.
- Identity numbers are stored only masked + as a keyed digest (`crypto.hash_kyc_identity`, digest domain unchanged so pre-rename values still match; the plaintext never reaches the DB); a pass records `kyc_provider` / `kyc_ref` / `kyc_verified_at`; once the number of non-deleted accounts with the same digest reaches `real_name_max_accounts_per_identity` (default 3) → 409 `account.realNameIdentityLimit`. `real_name_enabled` controls whether KYC can be submitted, `real_name_required_for_recharge` whether top-ups / instance creation require a verified identity — the gate is inert when the compliance profile offers no KYC form (`current_profile().kyc_form is None`). Invariant: the latter requires the former.
- Password login: the four buckets count → user lookup → **the read-only transaction is committed and the connection returned first** → bcrypt (dedicated 4-thread pool `core/security._BCRYPT_EXECUTOR`, 64 in flight, beyond that 429 without queueing) → refund / reset on success; a successful registration counts `superdl_user_signup_total`, a successful code send counts `superdl_verification_sent_total{channel, purpose}`.
- SSH keys: 50 per user, 20 additions per hour (`MAX_SSH_KEYS_PER_USER`); instance creation fetches keys by id set in SQL (`ssh_keys_by_ids`).
- Registration requires the terms checkbox and, in the same transaction, records one consent each for terms / privacy against the currently published version.
- Deletion is executed as anonymisation: both handles and `email_verified_at` become NULL (the handle is free for a new account), KYC name / masked identity / provider / ref / verified_at are cleared, `kyc_identity_hmac` is kept for the per-identity cap, every session is revoked; `balance_ledger` and bills are kept under legal obligations. The execution request must carry an operator `note`, written back to `account_deletion_requests.note` (the same column as the rejection reason).
- Every write goes through the audit middleware (actor / ip / result).
