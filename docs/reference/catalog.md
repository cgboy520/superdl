# Catalog

SKU management (admin CRUD), the user-side market query, the platform image catalog and approximate stock.

## Data model

- `skus`: name, gpu_model, tier (dedicated / shared / cpu), mig_profile?, gpu_cores_pct, vram_gb, oversell_cores numeric(4,2), pool_label, vcpu, mem_gb, disk_gb (includes the 100G instance disk), price_hourly numeric(12,4), max_gpus_per_instance, cuda_max, period_enabled (default true), spot_enabled (default false), status (on/off)
- Field conventions for CPU SKUs (tier=cpu): `gpu_model=""`, `gpu_cores_pct=0`, `vram_gb=0`, `mig_profile=NULL`, `max_gpus_per_instance=0`; `price_hourly` is the whole-machine hourly price (for GPU SKUs it is the per-card price). The cross-field rule lives in one place, `catalog/schemas.py::cpu_spec_error`: SKU creation calls it from the `SkuCreate` model_validator (422), SKU updates call it from `service.admin_update_sku` after merging the final state (400 + `message_key`). For GPU SKUs those three fields must not be 0.
- `images`: framework→version→python→cuda→image_ref, prewarm_enabled; prewarming in [images.md](./images.md)

## Contract

| Endpoint                                   | Role / auth          | Notes                                                                                                                                                                                                                                                                                                                                            |
| ------------------------------------------ | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `GET /api/v1/skus?tier=&gpu_model=`        | anonymous            | Listed SKUs only; includes available_count (computed per request from the node inventory, all SKUs in one batch), `period_enabled`, `spot_enabled`                                                                                                                                                                                               |
| `GET /api/v1/images`                       | anonymous            | Platform image catalog; `is_prewarmed` is computed                                                                                                                                                                                                                                                                                               |
| `GET /api/admin/v1/skus`                   | ops/finance/readonly | SkuAdminOut includes `capacity_gpus / sold_share / actual_oversell`                                                                                                                                                                                                                                                                              |
| `POST /api/admin/v1/skus`                  | ops                  | Create; `period_enabled` omitted = true; `spot_enabled` omitted = false                                                                                                                                                                                                                                                                          |
| `PATCH /api/admin/v1/skus/{sku_id}?force=` | ops                  | `pool_label` + `mig_profile` may change (as a pair, only while unlisted; changing either while on sale → 409 `CONFLICT`). Business-key collision → 409 `skuBusinessKeyExists`. `status→on` hard-checks "the inventory has a Ready node whose model `model_matches` and whose pool matches", failure → 409 `SKU_NOT_SELLABLE`, `force` skips it   |
| `GET /api/admin/v1/skus/capacity-preview`  | ops/readonly         | query `pool_label&gpu_model&gpu_cores_pct&oversell_cores&vram_gb&vcpu&mem_gb` → `{matching_nodes, ready_gpus, total_gpus, est_instances, warnings[]}`; pure DB, hami pool est = ready_gpus × ⌊100×oversell/pct⌋. Empty `gpu_model` = CPU SKU preview: nodes matched by pool only, `ready_gpus/total_gpus` always 0, est via `sellable_cpu_slots` |

`capacity_gpus / sold_share / actual_oversell` are assembled by adminapi from the catalog, nodes and orchestrator services; catalog has no reverse dependency.

## Rules and invariants

- SKU changes affect new instances only: an instance snapshots `price_hourly` and the spec when stored.
- SKU create / update is admin only, per-admin `admin-pricing` bucket of 20 per hour. Price-change alert (`catalog/service.py::_alert_large_price_change`, non-blocking): the baseline is `detail.before.price_hourly` of the earliest successful `PATCH` of that SKU within 24 hours in `audit_log` (the pre-change price when there is none); a cumulative change of ≥ 50 % against the baseline writes a critical `admin_alert` (24-hour cumulative SKU price change); when the cumulative rule does not fire, a single-step change of ≥ 50 % writes a warning (large SKU price change).
- SKU business key `(gpu_model, tier, pool_label, mig_profile, gpu_cores_pct, vcpu, mem_gb)` is a unique index (NULLS NOT DISTINCT); a duplicate create is 409.
- Approximate stock is estimated per (pool, canonical model): the source is `node_specs` (written by the 60 s patrol, only idle cards of Ready nodes count), the request path never calls K8s; computed per request, not cached.
- Soft admission on the creation path: when the inventory clearly shows insufficient allocatable capacity for that (pool, model) → 409 `NO_CAPACITY`; no inventory data lets the request through. No stock reservation; the scheduling result is final.
- Sellable instances per card in the hami pool = ⌊100 × oversell_cores ÷ gpu_cores_pct⌋, integer-divided as Decimal in one place, `catalog/service.py::sellable_per_gpu` (kata / mig always 1); (pool, canonical model) matching lives in one place, `nodes/service.py::matching_specs`. Market stock, soft admission, the admin capacity column and the capacity preview share these two definitions.
- CPU SKU stock is defined in one place, `catalog/service.py::sellable_cpu_slots`: per Ready node take `min(⌊budget vCPU ÷ sku.vcpu⌋, ⌊budget memory ÷ sku.mem_gb⌋)` and sum. In the cpu pool the whole machine's vCPU / memory count; in the hami pool each node is capped by the policy `gpu_node_cpu_instance_vcpu_cap` cores with memory scaled proportionally, and cap=0 means that node sells none. This is an upper-bound estimate, not a live remainder.
- CPU SKUs match nodes by pool only, not by model (`nodes/service.py::pool_specs`). The listing hard check only verifies "the pool has a Ready node" and reports `catalog.skuNotSellableCpu`; soft admission shortage reports `orchestrator.noCapacityCpu`.
- The admin SKU list renders `capacity_gpus / sold_share / actual_oversell` as "—" for CPU SKUs.
- `period_enabled` (default true) and `spot_enabled` (default false) decide whether the SKU accepts subscription orders and whether it is offered as spot, independent of `tier` / `pool_label`. When false the matching chip on the market page is greyed, and the server catches direct calls in `orchestrator.create_instance` (`orchestrator.periodNotEnabled` / `orchestrator.spotNotEnabled`).
- Changing these two switches affects new orders only. Sold subscriptions expire as usual and renew at the `subscriptions.unit_price` list-price snapshot; running spot instances keep billing at their snapshot price and may still be reclaimed (escaping the reclamation risk requires the user to call `/to-on-demand`, see [orchestrator.md](./orchestrator.md)). Definitions in [billing.md](./billing.md).
- Oversell parameters are pure pricing parameters and are not passed to scheduling.
- Listing is a hard check (may be forced); create and edit are soft checks (capacity preview warns, saving is allowed).
- Unlisted SKUs are invisible to users; readonly is read-only everywhere, finance cannot change SKUs.
- The tier is a sales classification; the source of truth for the isolation mechanism is `pool_label`. `tier` is only dedicated / shared / cpu; "shared · standard / shared · economy" are derived from the pool (mig = hard-partitioned standard, hami = soft-partitioned economy), mapped in one place on the frontend, `packages/ui/src/status.ts::skuVariant`. The cpu tier is not split by pool in the UI.
- The mig pool is hardware-enforced isolation, the hami pool is a CUDA-level software limit (root inside the container can bypass it): the hami pool is only for performance isolation / cost optimisation. The tier table is in [security.md](./security.md).
- A SKU on sale cannot change pool or MIG slice; unlist first or create a new SKU, `force` does not allow it.
- Tier and pool must pair (`dedicated⇔kata`, `shared⇔mig|hami`, `cpu⇔cpu|hami`), and the MIG slice and the mig pool are present or absent together: SKU creation and pool changes share `catalog/service.py::_check_tier_pool`, the pairing table is `core/gpu_adapter.TIER_POOLS`. The shared tier is additionally gated by the operations switch `SUPERDL_SHARED_TIER_ALLOWED_POOLS` (default `mig,hami`; dropping hami means "shared tier sells MIG only", empty stops selling the shared tier). The admin form only lets operators pick the display tier; tier and pool_label are derived.
- SKU names are structured (gpu_model + tier); the DB stores no localised display name.
- When creating a SKU from cluster resources, the model dropdown comes from the node inventory, see [nodes.md](./nodes.md).
