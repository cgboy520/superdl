# Private-network gateways

Connects a tenant's own network (office, data centre, cloud VPC, SD-WAN POP) to the tenant's instances. One gateway = one platform-run Pod that dials the tenant's VPN endpoint (WireGuard, IPsec IKEv1/v2, OpenVPN, or an openconnect-family SSL VPN: AnyConnect / ocserv, Fortinet, GlobalProtect, Pulse / Ivanti, F5, Array), relays TCP between the tunnel and the cluster and, with whole-subnet access (L3) on, routes between attached instances and the tunnelled networks. Instances keep their baseline security context; only the gateway Pod holds network privileges, in its own namespace, plus the platform's attach init container that configures an attached instance's own network namespace before the workspace starts. The image and its agent are in [deploy/netgw](../../deploy/netgw/README.md); the design choice is in [decisions.md](../decisions.md).

What a tenant gets:

| Direction          | Mechanism                                                                                                                                                                                              |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Instance → network | Named forwards: instances connect to `<forward name>:<port>`; the gateway connects to `target_host:target_port` inside the tunnelled networks                                                          |
| Instance → network | SOCKS5 at `socks5h://<gateway name>:1080` (CONNECT only); host names resolve on the gateway, so split-DNS domains work; destinations must be inside the tunnelled ranges                               |
| Network → instance | Instance forwards: the tenant network connects to `<tunnel address>:<port>`; the gateway connects to the instance's `target_port`                                                                      |
| Both (L3)          | Attached instances get an address in the gateway's instance network and a `netgw0` interface routing `remote_cidrs`: any protocol, any port; routed (both directions) or NAT (instance → network only) |

Relayed traffic leaves the gateway with the tunnel address as source, so the tenant side routes one address and never sees the cluster ranges; overlapping tenant ranges are independent (each gateway has its own network namespace). L3 traffic carries the instance address (routed) or the tunnel address (NAT); cluster ranges never enter the tunnel.

## Data model

- `net_gateways`: `uuid` unique, `user_id` (owner of a personal gateway, creator of an organization one), `org_id?` (set: an organization gateway, see [orgs.md](./orgs.md); CHECK: it carries `config.l3`), `name` (personal: DNS label, partial unique `(user_id, name) WHERE org_id IS NULL` and unique per user together with forward names; organization: partial unique `(org_id, name) WHERE org_id IS NOT NULL`), `protocol` (CHECK ∈ {wireguard, ipsec, openvpn, openconnect}), `status` (CHECK ∈ {active, deleting}), `config` jsonb (`remote_cidrs`, `local_address?`, `dns?`, `l3?` = `{cidr, nat, address (hub = first host), hub_public_key, routes_at}`, `tunnel` = the non-secret protocol parameters), `secrets_encrypted` (AES-GCM JSON of keys / PSK / passwords / the OpenVPN profile / the hub private key, AAD `netgw:<uuid>`), `public_key?` (WireGuard, generated by the platform), `generation` / `applied_generation`, `tunnel_up`, `tunnel_changed_at?`, `pod_phase?`, `checked_at?`, `idempotency_key?` + `request_fingerprint?` (the fingerprint covers secret presence, never secret values)
- `net_gateway_forwards`: `gateway_id` (FK, cascade), `user_id`, `kind` (CHECK ∈ {intranet, instance}), `name` (unique per user), `port`, `target_host?` (intranet), `instance_id?` (instance), `target_port`; CHECK `(kind = 'intranet') = (target_host IS NOT NULL AND instance_id IS NULL)`; partial unique `(gateway_id, port) WHERE kind = 'instance'`
- `net_gateway_attachments`: `gateway_id` (FK, cascade), `user_id` (the instance's owner; a member on an organization gateway), `instance_id` (unique: one gateway per instance), `address` (unique per gateway), `public_key`, `private_key_encrypted` (the instance's hub key, AAD `netgw-attach:<instance uuid>`), `created_at`

Derived `state` (not stored): `deleting` (status) → `applying` (`applied_generation < generation`) → `connected` / `disconnected` (`tunnel_up`, the gateway Pod's readiness = the agent's tunnel check).

## Rules and invariants

### Input

- Tunnelled networks (`remote_cidrs`): 1–16 IPv4 networks, prefix /8 or longer, pairwise disjoint, never overlapping 0/8, 127/8, 169.254/16, 224/4, 240/4, `SUPERDL_TENANT_POD_CIDR` or `SUPERDL_TENANT_SERVICE_CIDR` (both must match the cluster).
- Tunnel address (`local_address`): required for WireGuard and IPsec, outside the reserved ranges; OpenVPN and openconnect take the server-assigned address (a value is rejected).
- Peer: a DNS name or a public IPv4 (`is_global`) outside the tunnelled networks; TCP peer ports (OpenVPN over TCP, openconnect) outside the tenant egress blocklist. The gateway NetworkPolicy blocks private destinations, so a name resolving to a private address cannot be reached either.
- No raw daemon configuration is accepted. WireGuard: peer key, optional PSK, endpoint, MTU; the gateway key pair is generated server-side and only the public key is shown. IPsec: PSK of 16–128 printable characters without `"` or `\`, identities from a fixed character set, proposal presets `default` / `compatible` / `modern`. OpenVPN: the client profile passes an allow-list (`modules/netgw/ovpn.py`, the agent keeps an identical copy and a test compares them): no scripts, plugins, file paths, management, routes, `redirect-gateway` or DNS options; inline `<ca>` / `<cert>` / `<key>` / `<tls-*>` blocks only. openconnect: `https://host[:port][/path]`, password on stdin, optional certificate pin.
- Names (gateway and forwards) are DNS-1035 labels of up to 40 characters and share one per-user name space: they become Services in the tenant namespace. Names that could collide with platform objects (32-hex prefixes, `netgw-`, `jupyter-`, `disk-`, `superdl-`, `kubernetes`) are reserved.
- Instance-forward listen ports avoid 53, 1080, 9101 and 20000–20063 (the agent's resolver, SOCKS, health and intranet-forward ports) and are unique per gateway.
- Instance network (`l3.cidr`): /16–/29 inside 10/8, 172.16/12, 192.168/16 or 100.64/10, outside the reserved and cluster ranges, the tunnelled networks and the tunnel address; the first host is the hub, up to 250 instance addresses (`max_attachments`). openconnect gateways are NAT only (`netgw.l3NatRequired`: the server assigns one address). While instances are attached, L3 cannot be turned off and its network cannot change (`netgw.l3InUse`); `nat` and everything else can.
- Limits: `SUPERDL_NETGW_MAX_PER_USER` personal gateways per user (default 2), `SUPERDL_NETGW_MAX_PER_ORG` organization gateways per organization (default 4), `SUPERDL_NETGW_MAX_FORWARDS` forwards per gateway (default 16); see [limits.md](./limits.md).

### Convergence

- Every change bumps `generation` and enqueues `netgw.apply` in the same transaction. The handler (tenant-mgr worker) renders the **current** row into the agent spec, ensures the tenant namespace and the gateway pull Secret, and converges the objects; it records `applied_generation = max(applied, rendered)`. Deletion sets `deleting` and enqueues `netgw.delete`, which removes the objects in the gateway namespace and in every tenant namespace holding one of its Services, then the row (forwards cascade). Every apply also sweeps the gateway's objects out of tenant namespaces it no longer uses (NetworkPolicy first, then the Services).
- Objects (`core/k8s/netgw.py`, all labelled `superdl.io/netgw=<uuid>`, never `superdl.io/managed`, which the instance reconciler would reclaim as leaked endpoints):

| Namespace                                                  | Object                                                                                                                                                                                                                                                                           |
| ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `superdl-netgw`                                            | Secret `netgw-<uuid>` (`spec.json`, `peers.json`), Deployment `netgw-<uuid>`, NetworkPolicy `netgw-<uuid>`, Service `netgw-<uuid>` (SOCKS), Service `netgw-<uuid>-<forward id>` per intranet forward, headless Service `netgw-<uuid>-hub` (L3)                                   |
| tenant                                                     | ExternalName `<gateway name>` and `<forward name>` (pointing at the Services above), ClusterIP `netgw-<uuid>-<forward id>` per instance forward (selector `superdl.io/instance=<instance uuid>`), headless Service `netgw-<uuid>-l3` (L3, selector `superdl.io/netgw-l3=<uuid>`) |
| each attached instance's namespace (organization gateways) | headless Service `netgw-<uuid>-l3`, NetworkPolicy `netgw-<uuid>` (attached Pods ↔ the gateway Pod, UDP 51820); the gateway namespace has no SOCKS Service                                                                                                                        |

- Deployment: one replica, `Recreate`, the spec hash as a Pod annotation (any change restarts the Pod); `dnsPolicy: None` with `127.0.0.1` (the agent's dnsmasq); node selector `node-restriction.kubernetes.io/superdl-netgw=true` (kubelets cannot set it, so a tenant node cannot attract gateways); egress bandwidth `SUPERDL_NETGW_BANDWIDTH_MBPS` (default 100). Container: uid 0, `drop: [ALL]` + `NET_ADMIN` / `NET_BIND_SERVICE` / `MKNOD`, no privilege escalation, read-only root, RuntimeDefault seccomp, no service-account token, readiness `/healthz` (tunnel up), liveness `/livez`.
- The gateway patrol (30 s, tenant-mgr, advisory lock) reads Deployment and Pod state: sets `tunnel_up` / `pod_phase` / `checked_at`; re-applies (generation + 1) when nothing is pending and the Deployment is missing or runs another image than `SUPERDL_NETGW_IMAGE`; tears down personal gateways of deleted accounts and every gateway of an organization that is no longer active (a deleted creator leaves an organization gateway alone); deletes Deployments without a row. Rows locked by a running task are skipped for that round.
- Instance forwards whose instance is released drop out of the rendered spec and are shown with `available=false`; attachments of released instances, and on organization gateways those whose owner is no longer a member, are deleted by the patrol (their gateway is re-applied).
- The data plane does not depend on the control plane: stop-the-world releases leave gateways and tunnels running.

### Whole-subnet access (L3)

- Gateway side: the agent runs the hub `hub0` (WireGuard, UDP 51820, `l3.address`) with one peer per attachment from `peers.json`. `peers.json` is outside the spec hash, so attaching or detaching never restarts the gateway; the kubelet refreshes the mounted Secret within about a minute and the agent reloads it on change. Each peer accepts only its own `/32`; its endpoint is the Pod's DNS name `<instance uuid>.netgw-<uuid>-l3.<the instance's namespace>.svc` (headless, `publishNotReadyAddresses`), re-resolved every 5 s, so restarted instances and gateways find each other again by name.
- Instance side: `build_pod_spec_with_cluster` asks `netgw.service.instance_attach` for the instance's attachment (none when the gateway is deleting, L3 is off, the owner is no longer a member of the gateway's organization, or the feature is off) and `build_instance_pod` adds, for user-namespaced dev Pods only: the label `superdl.io/netgw-l3=<gateway uuid>`, `hostname` / `subdomain` for the headless Service, the Secret `netgw-attach-<instance>` (owned by the instance, rewritten on every start, deleted with it) and the init container `netgw-attach`: the gateway image running `python3 -m netgw_agent.attach`, uid 0 of the Pod's user namespace, `drop: [ALL]` + `NET_ADMIN` only, read-only root, no environment, the Secret as its only mount. It builds `netgw0` (instance address, the hub as the only peer, `remote_cidrs` routed through it) and exits; the workspace container that follows has no `NET_ADMIN`, so it uses the interface but can neither read its key nor change its routes or addresses.
- Forwarding (agent nftables): only hub ↔ `remote_cidrs` (NAT: outbound only, masqueraded to the tunnel address); everything else, including tunnel → cluster, is dropped; cleartext for `remote_cidrs` never leaves the Pod uplink. Routed mode needs the tenant side to route `l3.cidr` into the tunnel (WireGuard AllowedIPs, IPsec traffic selectors, OpenVPN `iroute`).
- Changes reach an instance on its next start: `pending_restart` marks attachments whose instance holds a Pod built (last entry into `creating` / `starting`) before the attachment or before `l3.routes_at` (the last change of `remote_cidrs`).
- Kata (VM-isolated) instances have no attach path; nodes running attached instances need the `wireguard` module.

### Organization gateways

- Owned by an organization ([orgs.md](./orgs.md)): created, changed, deleted and attached by its owners and admins under the organization row lock (organization → gateway → attachments). Whole-subnet access only: no SOCKS, no forwards, L3 cannot be turned off. `user_id` records the creator only; no personal endpoint ever reaches an organization gateway (every personal query carries `org_id IS NULL`), whatever the creator's role later becomes.
- Attachments: owners and admins attach members' unreleased dev instances; members cannot attach but can always detach their own (`DELETE /api/v1/netgw/attachments/{instance_uuid}`); the member is notified of both. One gateway per instance, personal or organization.
- Membership: removing members (leave, removal, account deletion) deletes their attachments on the organization's gateways and re-applies them in the same transaction (listener registered from `app/wiring.py`); dissolving marks every organization gateway `deleting`. The apply removes the member's namespace from the gateway policy and deletes the namespace's `netgw-<uuid>` policy within seconds; the hub drops the peer when the kubelet refreshes `peers.json` (about a minute). `render_input` and `instance_attach` ignore non-members' attachments, and the patrol deletes them.
- The gateway Pod carries no `superdl.io/tenant` label and its template never depends on membership, so attachments and membership changes never restart it; its tenant-side objects follow the attached instances' namespaces (`NetgwSpec.l3_namespaces`, outside the spec hash).

### Network boundary

- The tenant NetworkPolicy admits, in both directions, Pods in `superdl-netgw` labelled `superdl.io/tenant=<that namespace>` (set only by the platform, on personal gateways only); without a gateway the rule matches nothing.
- The gateway NetworkPolicy of a personal gateway admits ingress from its tenant's namespace only (any port); egress to the cluster DNS, to the peer ports on the internet (private ranges excepted), and to its tenant's namespace (instance forwards). An organization gateway's admits, both ways, only Pods labelled `superdl.io/netgw-l3=<uuid>` in the attached instances' namespaces, on UDP 51820 (no tenant rule at all without attachments); each such namespace adds the matching `netgw-<uuid>` policy for the attached Pods, on top of the unchanged tenant default policy. Decapsulated tenant traffic never crosses the Pod interface, so the platform policies apply to the tunnel's outer packets only.
- The agent connects forwards and SOCKS only to addresses inside `remote_cidrs` and reverse relays only to the Pod / Service ranges, so the gateway is never an egress proxy for the internet.
- The gateway only initiates: no public listener, no port pool. Tenants allow the addresses in `SUPERDL_NETGW_EGRESS_IPS` on their side.
- Admission: policy ① lets platform service accounts write in `superdl-netgw`; policy ④ (`superdl-global-pod-guard`) limits Pods there to the digest-pinned `…/superdl-netgw@sha256:` image, the three capabilities, no escalation, no token and only their own `netgw-*` Secret plus emptyDir volumes. The namespace is PSA `privileged` (NET_ADMIN is outside `baseline`) and carries no `superdl.io/managed` label. In tenant namespaces policy ② admits `NET_ADMIN` for one container only: an init container named `netgw-attach` of a user-namespaced Pod, running the digest-pinned gateway image with a read-only root, no environment, no `restartPolicy` and its `netgw-attach-*` Secret as its only, read-only mount (see [security.md](./security.md)).
- A personal gateway's hub port needs no extra rule: the tenant and gateway policies already admit each other on every port.

### Enabling

1. Build and push the image ([deploy/netgw](../../deploy/netgw/README.md)); set `SUPERDL_NETGW_IMAGE` to the `…/superdl-netgw@sha256:…` reference (prod refuses tags) and `SUPERDL_NETGW_EGRESS_IPS` to the gateway nodes' public egress addresses.
2. On each gateway node load `wireguard`, `tun`, `xfrm_user`, `esp4`, `nf_tables`, `nft_chain_nat`, `nft_masq`, `nft_ct` (`/etc/modules-load.d/superdl-netgw.conf`) and label it `node-restriction.kubernetes.io/superdl-netgw=true`; on nodes running instances load `wireguard` (L3 attachments).
3. Before the first release that ships the feature, create the `superdl-netgw` namespace out of band (apply its `Namespace` document from `deploy/app/k8s/00-namespace-config.yaml`): `scripts/release.sh` dry-runs every rendered object server-side, and the Role inside a namespace that does not exist yet fails that dry-run. Then release; from there on the namespace, its labels and its RBAC are converged with `deploy/app/k8s`.

Gateways are not billed separately; the per-user and per-gateway limits and the bandwidth cap bound their footprint.
