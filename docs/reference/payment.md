# Payments

Top-up orders, pluggable payment channels (the `payment_channels/spec.py` registry), and the callback / order-query loop. Code lives in the billing module (`payment_channels/` — `base.py` protocol and shared helpers, `spec.py` registry, `mock.py` / `wechat.py` / `alipay.py` / `stripe.py` channels, `__init__.py` factory — and `webhooks_router.py`).

## Data model

- `orders`: order_no unique, user_id, amount numeric(14,2) >0, currency (ISO 4217 = platform currency at creation), channel (registry name), channel_txn_id unique?, payment_url?, channel_ref?, status (pending/paid/closed/failed), idempotency_key (unique together with user_id), paid_at, expires_at, channel_reversed_at? (first arrival of a channel reversal notice), channel_reversal_resolved_at? / channel_reversal_action? (release / chargeback, manual handling; CHECK)
- `refund_requests`: refund_no unique, user_id, order_no, amount numeric(12,2) >0, reason, status (pending/approved/paid/rejected/cancelled), review_by/review_at/review_comment, payout_channel (offline/alipay_transfer/wechat_transfer)/payout_ref/payout_at, idempotency_key (unique together with user_id); a partial unique index guarantees at most one active (pending/approved/paid) request per order
- `invoice_requests`: user_id, period (YYYY-MM, month boundaries in the billing time zone, `timeutil.billing_period`), title_type (personal/company), title, tax_id?, email, amount numeric(12,2) (computed server-side per period), status (submitted/issued/rejected), invoice_no?, reject_reason?, issued_by/issued_at, idempotency_key (unique together with user_id); a partial unique index guarantees at most one non-rejected request per (user_id, period)

## Rules and invariants

### Channels

- WeChat Pay uses APIv3 (wechatpayv3); signature verification supports the WeChat Pay public-key mode only (`PUB_KEY_ID_*`; public key and key id are required channel settings); Alipay uses face-to-face payment (alipay-sdk-python): precreate + RSA2 plain public-key mode, with order query.
- Stripe (`payment_channels/stripe.py`, presentation `redirect`, any platform currency): each order becomes a Checkout Session (`mode=payment`, `client_reference_id` = order_no, PaymentIntent metadata `order_no`, `expires_at` clamped to Stripe's 30 min–24 h window with a 60 s buffer above the minimum, idempotency key `superdl-recharge:<order_no>`; the SDK client runs on the shared 5 s connect / 10 s read timeouts); `payment_url` is the hosted page, `channel_ref` the session id. The webhook `/api/v1/webhooks/stripe` verifies `Stripe-Signature` (5 min tolerance) and maps `checkout.session.completed` / `async_payment_succeeded` with `payment_status=paid` → credit (txn id = PaymentIntent), `async_payment_failed` / `expired` → failed, `charge.refunded` / `charge.dispute.created` → reversal freeze looked up by PaymentIntent (`handle_callback` resolves orders by `order_no` or `channel_txn_id`), anything else → acknowledged and ignored. `query_order` retrieves the session (`complete`+`paid` → paid, `expired` → closed). Card refunds stay off-channel (finance refund flow, payout `offline`). Config group `payment_stripe`: `payment_stripe_enabled`, `stripe_secret_key` (`sk_`/`rk_` `test|live`), `stripe_webhook_secret` (`whsec_`); a test key in prod is a config warning. Local rehearsal: `stripe listen --forward-to localhost:8000/api/v1/webhooks/stripe` with test keys.
- Registry `payment_channels/spec.py::CHANNELS` — `ChannelSpec(name ≤16, presentation qr|redirect, enabled_key, config_keys, factory, webhook_path, ack, currencies, payout_channel, dev_only, supports_query)`; `get_channel` / `enabled_channels` / the webhook router / `/site-config.payment_channels` (`[{name, presentation}]`) / refund payout options (`AdminRefundOut.order_payout_channel` = the order channel's `payout_channel`, offered next to `offline`) all read it. Adding a channel = one entry + one module. `PaymentChannel.create_payment(order, return_url=, cancel_url=) -> PaymentInit(url, channel_ref)`; `orders.payment_url` (2048) / `orders.channel_ref` persist them.
- An enabled channel whose `currencies` exclude the platform currency is a config error (`payment_config_warnings`, shown on the admin config page and logged at boot) and every order on it is refused.
- `PaymentChannel.query_order` is the unified order-query seam; the mock channel keeps its own channel-side ledger.
- Every blocking SDK call (construction, order creation, order query, callback verification) runs on the dedicated thread pool `payment_channels.run_in_sdk_pool` (8 threads), never on the default executor shared with bcrypt; WeChat `timeout=(5, 10)`, Alipay `timeout=10`. Instances are cached by configuration fingerprint.
- Channel credentials and switches are configured in the admin console, see [platform-config.md](./platform-config.md).

### Callbacks and order queries

- Callbacks are idempotent through the `channel_txn_id` unique constraint; a callback whose amount does not match is rejected and alerted.
- Callback timestamp freshness window ±15 minutes (`CALLBACK_FRESHNESS_SECONDS`; WeChat `Wechatpay-Timestamp` / Alipay `notify_time` in Beijing time); outside the window or missing = signature failure; channel retries are re-signed with a fresh timestamp and unaffected.
- Before a WeChat callback reaches the SDK, `Wechatpay-Serial == wechat_public_key_id` is checked: an unknown serial is rejected outright.
- An Alipay notice with a non-empty `refund_fee` (partial refund, `trade_status` still TRADE_SUCCESS) is treated as a reversal notice (`CallbackResult.refund_amount`), not as a success callback.
- Every callback, reversals included, must name the order's own channel and, when it reports a currency, the order's currency (`billing.callbackChannelMismatch` / `billing.currencyMismatch`); success amounts are quantised in the order's currency before comparison. A reversal that arrives before the success event (webhooks are unordered) sets `channel_reversed_at` on the still-pending order instead of failing it; the later success credits and freezes the amount in one transaction.
- A reversal notice on a credited order: the equal amount is frozen only the first time the flag is set; manual handling (`/finance/reversals/{order_no}/resolve`) writes `channel_reversal_resolved_at` + `channel_reversal_action` and **does not clear `channel_reversed_at`**, so a replay of the same notice only leaves a trace and a count (`superdl_payment_channel_reversed_total`) without freezing again. Released orders regain refund and invoice eligibility, charged-back ones do not. Release is a single-operator action and alerts every time (`PaymentReversalReleased`, `superdl_payment_reversal_resolved_total{action}`).
- WeChat callbacks check the resource's mchid/appid against our own merchant; the Alipay signature string drops empty parameters as the official rules require.
- **The Alipay callback response must be the plain text `success`.**
- Order creation passes the expiry to the channel (WeChat `time_expire` RFC3339 / Alipay `timeout_express` minutes), in step with the local close time.
- A valid, amount-matching success callback arriving after the order was closed is credited automatically; failed orders and amount mismatches are still rejected. A non-zero `superdl_payment_closed_order_rescued_total` means the local close TTL and the channel expiry are out of step.
- The order-query poller converges lost callbacks every 2 minutes (advisory lock 1007): it scans pending orders older than 60 s and failed / closed orders of the last 48 h (closed bounded by `expires_at`); an order paid on the channel side is credited through the same path as a callback; a single credit failure counts `superdl_payment_recover_failed_total` and is skipped; leftovers are handled by the anomaly list + manual backfill.
- Manual backfill is channel-verified: the server queries the channel live (outside the lock, 15 s timeout, re-checked under the row lock before posting) and credits only when paid with a matching amount; pending / closed / failed can all be backfilled. Supports Idempotency-Key: a replay with the same key on a credited order returns the current state (`orders.backfill_idempotency_key`). See [admin.md](./admin.md). Channel results (`CallbackResult` / `QueryResult`) carry the channel-reported `currency` (WeChat from the wire, Alipay fixed CNY, mock optional); callbacks, poller recovery, `verify_order` and backfill all require it to equal `orders.currency` when reported (`billing.currencyMismatch`, counted in `superdl_payment_callback_mismatch_total`).

### Refunds and invoices

- No refunds through the channel. The loop: the user applies → finance approves (wallet untouched) → a second admin registers the offline payout (`payout_by ≠ review_by`, application-level 409 + DB CHECK) → the wallet is debited in the same transaction (ledger type=refund, with balance_after); at payout time the balance is re-checked under the wallet row lock to be ≥ the refund amount, otherwise 409 and the request can be cancelled.
- Paid orders in an already invoiced (issued) period cannot be refunded; the request takes `FOR UPDATE` on the period's active invoice request row. Payout registration does not re-check whether the period has been invoiced since.
- Invoices are issued per period, one per calendar month, and only for periods before the current billing month (`current_billing_period`); the invoiceable amount = paid top-ups of the period (excluding channel reversals) − refunds of the period's orders (paid + in flight, attributed by the linked order's payment period) − already requested / issued amounts, computed only by the server; at issue time it is recomputed under a row lock by the current rule, and a mismatch is a 409 rejection to re-apply; after a rejection the same period can be requested again.
