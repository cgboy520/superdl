# Admin console

`apps/admin`: dark NOC-style admin console, roles admin/ops/finance/readonly. Visual spec in `docs/ui-ux-spec.md`.

## Data model

- `admin_users`: username unique, password_hash, role (admin/ops/finance/readonly), status
- `admin_adjustments`: adjustment orders, initiate → review → effective

## Rules and invariants

- Admin and user APIs are physically separated, tokens are not interchangeable; the sidebar menu is filtered by role (`lib/menu.ts` aligned endpoint by endpoint with the backend `require_roles`), a URL typed directly is caught by the backend 403.
- Deep-link parameters (views operators pass to each other always live in the URL): `/tenants?tenant=<id>` opens the tenant drawer (`TenantLink` and alert `tenant` targets carry it); `/tenants?tab=instances&inode=<node>` shows instances by node (linked from the "used" column of the node table); `/nodes?node=<name>` (opens the node detail drawer) and `/nodes?status=<Ready|NotReady|Cordoned|Missing>`; `/finance?day=<YYYY-MM-DD>` (reconciliation day); `/tickets?id=<id>`; `/platform?group=<group>` (current configuration group); `/images?image=<id>` (expands that image's node cache panel; failure counts are clickable). The alert → target mapping is in `lib/alertLink.ts`.
- High-risk `ReasonAction`s always carry a `target` (tenant #id · masked handle / instance name · uuid prefix / node name / refund number etc.), both dialog steps echo the target and the second confirmation also echoes the reason; Ctrl/⌘+Enter in the reason box moves to the next step; disabled states stay focusable (`aria-disabled`).
- Bulk operations (`BulkBar` + `runBulk`; the backend has no bulk endpoints, calls run concurrently one by one and are summarised as "N succeeded / M failed"): bulk alert ack, bulk dead-letter replay / discard, bulk settlement-gap replay, bulk node cordon / uncordon (one reason applies to every selection, each audited individually).
- Row actions go through `RowActions` (≤ 1 primary + 1 secondary + `RowMoreMenu`, dangerous items last; refund "cancel", image "delete" and instance "force reclaim" live under "more"); conditional disabling always uses `GatedButton`; **every filter** goes through `FilterBar` (clear filters + server-side total) and into the URL; search box ↔ URL via `useUrlCommittedInput`; status tags via `StatusTag` (accepts only the status maps from packages/ui, including `nodeStatusMap` / `severityMap`); cursor-paged tables via `CursorTable` (Table + error empty state + LoadMore in one place, the query side passes a structured `CursorListQuery`).
- Command-palette entity search: digits only → tenant id (opens the drawer directly); ≥ 6 hex digits → instance uuid prefix (→ tenant page, Instances tab); node names / SKU names / service names are matched from cached lists; page navigation is sectioned by sidebar group.
- The menu's source of truth is `MENU` in `lib/menu.ts` (shared by the sidebar and ⌘K; `group` has four groups: overview / resources / business / governance, order `MENU_GROUP_ORDER`), visibility filtered by `MENU_ROLES`; key-set consistency is guarded by `lib/menu.test.ts`.
- Table density and fixed columns: `adminThemeComponents.Table` unifies 13px / `cellPaddingBlock 8` (top-level tables do not use `small`); numeric and money columns are right-aligned, identifier columns use `Mono`; tables with `scroll.x ≥ 1000` fix the identifier and action columns and are `sticky` (top bar height `layout.topBarHeight`), the fixed right column must be the last one; wide-table pages use `PageContainer width="full"`; polling pages hang a freshness bar on the page header (`useAutoRefresh` + `PageHeader.freshness`); edit drawers have submit + cancel in the footer, `useLeaveGuard`, and widths only from `drawerWidth.md/lg`; the environment badge decision lives in `lib/environment.ts` (no environment endpoint yet, decided by build mode for now); recovery-direction actions (uncordon / unfreeze / list) only take a reason, no second confirmation.
- Non-route files under `src/routes/` start with `-` (tanstack router's routeFileIgnorePrefix).
- Admin login rate limiting has four buckets, counting before bcrypt and deciding afterwards (`core/loginguard.login_attempt`): `admin-login:{ip}:{username}` and `admin-login-acct:{username}` reset on success, `admin-login-ip:{ip}` refunds this attempt on success, `admin-login-acct-daily:{username}` counts only after a failure; TOTP verification uses `admin-mfa:{admin_id}`. Limits in [limits.md](./limits.md).
- The other three buckets count before bcrypt and decide afterwards (atomic under concurrency), then reset / refund on success; the daily account bucket only counts after failures and does not gate admission.
- readonly is read-only everywhere; finance can write only in the finance area.
- PII plaintext reads have one gate (`adminapi/service.ensure_reveal_allowed`, shared by tenant KYC identity and invoice title / email): readonly never gets plaintext, `reason` is required (≥ 2 chars), the normalised reason goes into the audit; every new plaintext outlet goes through it. Names are masked by `account.mask_id_name` (first character kept), emails / phones by `core/handles.mask_handle`; list pages and CSV exports use the same masking level.
- Invoice `tax_id` is not masked (the schema forces it empty for personal invoices); masking covers only the title and the email.
- Adjustment review reads with a `with_for_update` row lock: the later of two concurrent reviewers sees a non-pending row and gets 409, and the ledger has exactly one adjust entry. The reviewer must not be the initiator and must be an account created before the adjustment was initiated.
- Adjustment initiation and manual backfill support Idempotency-Key (adjustments land on the `(created_by, idempotency_key)` unique constraint; backfill lands on `orders.backfill_idempotency_key`, and a replay with the same key returns the current state).
- Announcement broadcast is a chunked bulk INSERT (⌈N/1000⌉ statements in one transaction) and reaches active users only.
- Backfill is channel-verified: the server queries the channel live and only posts when the order is paid and the amount matches.
- "Oversell ratio vs utilisation" is aggregated weighted by pool (metering supplies per-instance hourly aggregates, orchestrator supplies the instance → pool mapping, adminapi assembles); pools without data return `null`.
- The bills shown in the admin console come from the same source as the user's.
- The three pricing / policy write entry points `POST /skus`, `PATCH /skus/{sku_id}` and `PUT /policies` are admin only and share the per-admin `admin-pricing:{admin_id}` bucket of 20 per hour (see [limits.md](./limits.md)); ops is read-only.
- `PUT /policies` writes one critical `admin_alert` in the same transaction when `spot_discount_pct` / `disk_price_gb_month` / `max_gpus_per_user` / `disk_grace_days` / `disk_frozen_days` / `period_discount_*` change by ≥ 50 % relative to the previous effective value (the title flags the sharp policy change, the body lists old → new value and the reason per key). Price-change alert rules are in [catalog.md](./catalog.md).
- The policy parameters page includes the five subscription keys (`period_discount_day` / `_week` / `_month` / `_year` and `period_expire_warn_days`) and the two spot keys (`spot_discount_pct` / `spot_grace_seconds`); ranges in [limits.md](./limits.md). Changes take effect immediately and only affect later quotes; the two spot keys are also delivered to the user console through `GET /api/v1/policies`.
- `spot_grace_seconds` has an additional cross-key cap (not above `creating_timeout_seconds` minus the scheduling margin); when exceeded the backend returns the error copy with the concrete cap, and the frontend must show it verbatim rather than compute its own.
- The daily reconciliation card covers subscriptions: the billed side includes `subscriptions.amount_paid`, the consumption side includes ledger rows with `ref_type='subscription'`, both over the same window (see [billing.md](./billing.md)).
- The "purchase mode" of the global instance table comes from `AdminInstanceOut.market`, the expiry from `AdminInstanceOut.subscription.expires_at`; admin and user consoles share the same batch back-fill path (`attach_instance_details`); on-demand instances have `subscription` null, rendered as "—".
- `OverviewPoolOut.gpu_spot_used` comes from the instance side (`orchestrator/queries.py::running_spot_gpus_by_pool`) and is a sub-segment of `gpu_used` (node inventory), capped as `min(spot, gpu_used)` during assembly; `gpu_used − gpu_spot_used` must not be taken as an exact "non-spot rented" figure.
- `running_spot_gpus_by_pool` must aggregate on the Python side, written like `running_gpu_share_by_pool`.
- The overview's `subscriptions_active` is the number of covered subscriptions, not an instance status count (a stopped monthly instance is still covered until its period ends).
- Every adminapi endpoint declares a response model (kind/group/source as Literal); frontend row types are re-exported from the generated contract, never hand-written.
- The "force reclaim" and "force stop" entry points are not merged: different reasons. Both use `ReasonAction`; reclaim additionally takes the preemption path (grace window + notification, see [orchestrator.md](./orchestrator.md)); force reclaim ends in stopped with the instance disk kept.
- High-risk actions: reason required → second confirmation → audit; colours are centralised in `adminColors`, messages go through `App.useApp()`.
